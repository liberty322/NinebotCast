# Ninebot Pro+ · 以 NinebotPro 为主的改造说明

## 一、先说清楚一个硬约束

你要的是「以 NinebotPro 为主去修改」。要做到字面意义上那句话，前提是能改它的源码——**NinebotPro 没有源码**。

- `xmz28/ninebot_pro` 仓库里只有 README、三张截图、一个 `docs/`，**没有任何源码**；
- iOS 包只是 release 资产（`ios-v1.0.1`），里面是一个 2.2 MB 的 arm64 二进制；
- 它是 Swift 编译产物，没有资源脚本、没有可注入的 JS、没有插件点。

所以「修改 NinebotPro 本体、让它直接认 CarWithin」只有一条技术路线：**改机器码**。这条路我实算过，走不通，原因是三处结构性差异同时存在：

| 环节 | NinebotPro（OXP 客户端） | CarWithin（`VideoOutputServer`） |
| --- | --- | --- |
| 握手 | 主动发 `hello`（几十个字段的字典）+ `display-settings` | 等客户端先发 `ready` + `display` |
| 格式协商 | 收 `video-format`，取里面的 `config`（base64 avcC） | 发 `format`（MSE 模式下可能干脆没有 `description`） |
| 二进制帧 | **24 字节头**：kind/stream/flags/seq/ptsUs/senderClockUs | **1 或 9 字节头**：`timed = tag==4\|\|5`，时间戳 BE64 |
| 触控/按键 | kind=16 / 17 的二进制消息 | JSON 文本消息 |

要打补丁就得同时重写：JSON 字典构造（`helloMessage` 里 400 多条指令拼出来的）、JSON 解析分支、以及帧头解析循环。这不是补丁，这是把两个函数整个换掉——而 Swift 的函数替换需要在二进制里手工拼机器码并重定位 Swift 运行时调用，成功率极低，且一改就崩。

**结论**：能做的、也有价值的那件事，是**用 NinebotPro 的组织方式重做一个 App**，把它的参数模型、校验边界、预设、自检、日志全部照搬，同时保留已经跑通的 CarWithin 取流。这一版就是这么做的。

## 二、CarWithin 逆向结果（这次补上的）

原生侧的服务端类：**`TDSCarKit.VideoOutputServer`**，一个 `NWListener` 上的自建 WebSocket 服务。

关键成员（符号表还原）：

```
start(port:securePort:width:height:fps:performance:showTouches:
      preferredViewer:browserAudio:airPlayStreamID:)
append(codec:Data:Codec:)          appendAudio(stream:stamp:AVAudioPCMBuffer)
handleHTTPRequest(Client)          upgradeWebSocket(headers:Client)
serveHTTPSSetup(to:)               reject(status:to:)
handleText(client:)                handleText(client:TouchPoint)
handleText(client:screenDimension:)
deliver(to:Frame:Client)           send(to:Data:Client)
replayGOP(to:)                     takeWebSocketFrame(from:Data)
updatePrimaryDisplay(changed:force:)
maximumViewers                     onTouches / onControl(CarPlay) / onKeyframeRequest
onDisplay(Browser) / onStruggling  / onAirPlayReady / onLog / onState
```

握手魔数 `258EAFA5-E914-47DA-95CA-C5AB0DC85B11` 和 `HTTP/1.1 101 Switching Protocols` 都在 `upgradeWebSocket` 里，确认是标准 RFC6455，**但不是 OXP**——整个二进制里没有一个 `oxp` 字样。

顺带确认 CarWithin 是一整套 CarPlay 接收端：`CarPlayInfo`、`PairVerify`、`IAP2Packet`、`AccessoryIdentityStore`、`BLEBootstrap`、`LocalTLSIdentity`、`CarPlayAudio`、`CarPlayMediaSession`、`CarPlayHLS`、`FragmentedMP4`、`H264Surface`、`VideoParameterSets`、`CarLifeOutput`。

`/stream` 这个路径字符串只出现在内嵌网页里，原生侧用的是内联短字面量——所以想靠改字符串把 `/stream` 变成 OXP 端点也不行，路径比较根本不在 `__cstring` 里。

## 三、这一版做了什么

工程：`work/ninebotpro-plus`（目标 `NinebotProPlus`，包名 `com.hanlin.ninebotpro.plus`，显示名 **Ninebot Pro+**，版本 1.0.1 / 3）。

### 1. 参数模型换成逆向出来的那一套

`Sources/StreamProfile.swift` —— 字段与判据逐条对应 `NinebotPro.StreamProfile.validated()`：

| 字段 | 边界 | 原文提示 |
| --- | --- | --- |
| width / height | 64–1920 偶数，w·h ≤ 1920×1080 | 「宽高须为 64–1920 之间的偶数，总像素不超过 1920×1080」 |
| fps | 5–30 | 与下两条共用一句 |
| bitrate | 250–8000 kbps | 「帧率须为 5–30，码率须为 250–8000 kbps，JPEG 质量须为 30–95」 |
| jpegQuality | 30–95 | 同上 |
| rotation | {0°, 90°, 180°, 270°} | 原版用 SIMD 四路等值比较，这里用枚举实现 |

另外按原版补了 `scaleMode`（适配/裁剪/拉伸）和 `codec`（H.264 / JPEG），以及仪表地址映射：**五寸 192.168.1.1、4.3 寸实验 192.168.169.1**。

### 2. 主界面按 NinebotPro 的分区重排

`Sources/NinebotProHomeView.swift`：仪表 → 画面源 → 参数 → 投屏控制 → 状态 → 自检 → 日志 → 关于。

- 参数区：宽高 Stepper、帧率/码率/质量滑杆、旋转与缩放选择器，**滑杆自带夹取**，越界不会崩；
- 画面源：CarWithin 地址、相册图片、相册视频、摄像头前后、测试图；
- 状态区：帧/包/实测 fps/帧均 KB/往返 ms/心跳/积压/丢帧，外加仪表主动要求帧率时的提示；
- 开始投屏前先过 `validated()`，不合法直接把原版提示显示出来，不会带着坏参数发 UDP。

### 3. 自检（不需要接仪表）

`Sources/SelfCheck.swift`，对应原版的 `CodecSelfCheck`，但做的是能立刻验证的部分：

- **参数边界**：8 组用例跑一遍，确认 63 宽被拒、481 高被拒、1921 宽被拒、1920×1080 通过、31fps/249kbps/96 质量被拒；
- **RTP 打包**：造一帧 3.5 个分片的假数据，逐包核对 20 字节头（`0x90`、`PT=32`、`[15]=1`、`[16]=0`、`[8..14]=0`）、时间戳 BE32、帧标识 `1024|ts&1023`、首包 `0x11`/尾包 `0x09`/中间 `0x01`、以及负载重组是否逐字节一致；
- **RTCP**：心跳包 `85 CC 00 04 …` 尾部 `02`、ping 包计数器落在 `[12..15]`。

这几项只要有一个字节错位就会红，比等仪表黑屏快得多。

### 4. 日志

`Sources/AppLogStore.swift`：环形缓冲 500 条，时间戳到毫秒，一键导出成 txt（`ShareLink`）。启动、换源、参数校验失败、开始/停止、自检结果都会写进去。

### 5. 保留的东西

投屏引擎没动：`CastEngine` / `RTPPacker` / `H264Encoder` / `UDPChannel` / `KCPChannel` / `BackgroundKeeper` / `LanScanner` 全是上一版验证过的代码。CarWithin 的 WebSocket 客户端 `CarWithinSource.swift`（846 行）原样保留，包括无 `description` 时用带内 SPS/PPS 兜底、`sniffNalLength` 自动识别长度前缀宽度。

## 四、怎么用

1. 装 IPA（未签名，用 TrollStore / 自签工具）。
2. 手机先连**仪表的 Wi-Fi**（五寸一般是 `192.168.1.x` 网段）。
3. 仪表地址按预设填，或者点「按参数填地址」。
4. 画面源选 **CarPlay**：先在 CarWithin 里接上 CarPlay，把它给的地址（形如 `192.168.1.20:9889`）填进来，点「使用 CarPlay 画面」。
5. 先点「运行本地自检」，全绿再点「开始投屏」。
6. 状态区的「心跳回应」开始涨，说明仪表认了；「往返 ms」有数，说明 RTCP 通了。

CarWithin 必须留在后台——iOS 不向第三方开放 CarPlay 视频出口，这是系统限制，不是实现问题。

## 五、还没做的

- **JPEG 通路**：参数模型和校验已经支持 JPEG（30–95 质量、`192.168.169.1`），但 `NinebotJPEGPacketizer` 那条逐帧 JPEG 切片还没接进引擎，4.3 寸预设目前仍会提示「未实现」。
- **相册视频的进度/暂停/循环**：原版有，这一版只做了「选中就播」。
- **自动开投**：原版检测到仪表进入接收态会自动开，这一版去掉了这个开关（没实现就别摆出来），需要手动点。
- **没在真机验证**。CI 只能证明编译通过，投屏效果要你上车试。
